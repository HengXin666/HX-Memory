# 盲审结论与 Wiki 范式终局判定

> 目的: 记录独立盲审 (2026-09-18) 对本仓库 Wiki 实现的审查结论、我方复现结果、缺陷修复清单, 以及**范式是否成立**的终局判定。
> 边界 (不写什么): 不评价外部产品; 不复述实现细节 (在 `src/wiki/`); 本文只记录"审查发现了什么、修了什么、结论是什么"。
> 与代码的关系: 已修复项逐条映射到 `src/wiki/` 与 `tests/s2/wiki.test.ts`; 未修复项显式列为遗留。

## 1. 盲审的启动方式与其独立程度

为避免"实现方自证", 本轮把 `src/wiki/` 全部代码、两份 A/B 脚本、新旧两套用例生成器交给一个**不共享本对话上下文的独立审查者**, 要求它只读代码与数据、逐条给出 `文件:行` 证据、发现不了问题就明说。

其核心指控**由我方独立复现**, 结果如下 (复现脚本 `.tmp/bench/audit-repro2.ts`)。

## 2. 决定性反证: 范式的前提在实测语料上不成立

盲审指控: "Wiki 侧根本没有聚合, 只是'一条目一小节 + 页头开销'的更差条目式"。

我方复现 (按**来源数**计数, 修正了我先前误用"正文行数"的错误口径):

| 时点 | 页面数 | 单来源页 | 多来源页 |
| --- | --- | --- | --- |
| 修复前 | 69 | 63 (**91%**) | 6 (9%) |
| 修复后 (8 项缺陷全修) | 64 | 60 (**94%**) | 4 (6%) |

**修复没让聚合变好, 反而略差。** 这不是实现缺陷 —— 根因是**语料性质**:

```text
语料 125 条 → 121 个不同主题词 (主题几乎不重复)
条目对 7750 对中, 共享 >=2 个内容词的只有 1231 对 (15.9%)
```

"一主题一页"要产生聚合, 前提是**同一主题出现多次**。本项目当前语料**每个主题基本只出现一次**, 因此:

> **聚合在数学上不可能发生** —— 125 条事实无论怎么编译, 都只能得到 ~125 张各有 1 条来源的页。
> 这不是"Wiki 错了", 而是"这批数据没有可供聚合的结构"。

## 4. 未修复的遗留 (诚实列出)

1. `matchPage` 无 IDF、无长度归一, 构造用例下会退化 (junk 页塞满查询词得 21 分 vs 精确短页 3 分)。在本语料上尚未由该机制主导结果。
2. 读-改-写非原子, `writeFileSync` 无 tmp+rename。同进程串行安全, **跨进程并发会丢更新**。
3. `slug()` 把 `"接口/域名"`、`"接口-域名"`、`"A.B"`、`"A B"` 压成同一键 —— 不同主题获得同一地址 (假合并风险)。
4. 命中判据依赖"页面正文包含源条目前 32 字", 该判据**可被被测方正文自证**, 属自导自演残留 (见 §5)。

## 5. 评测方法的作废声明

盲审判定我方 A/B 实验**不能支持任何范式结论**, 我方接受并复现其理由:

1. **C 与 D 是同一段代码跑两遍** —— `drill` 标志不进打分, 只多一段 `"\n来源:"`; 48 个 case 中 15 个选中集合完全相同, 总 token 差 13。并列成两个臂 = 重复计数冒充交叉验证。
2. **命中判据可平凡操纵** —— 32 字 probe 在全库 100% 命中, 但预算窗口内只剩 7.8%, 与报出的 0.078 完全吻合。C/D 的分数量的是"多少 gold 正文挤进预算", 与排序质量无关。
3. **两臂 oracle 不同族** —— A 用真实 entry id, C/D 用正文子串包含。不同测量仪器的差值不能读作范式差异。
4. **gold 归属不校验 session** —— 77 个 gold 中 53 个 (69%) 的 `sourceRef` 不含本 case 的 session, 系统性偏向"近期/全局/广泛"的系统。

因此前一轮报告的 `A=0.286 / C=D=0.078` **作废, 不再作为任何结论的依据**。

## 6. 终局判定

**"一主题一页"在本项目当前语料上未成立**, 但**不成立的根因是数据而非设计**:

- 语料 121/125 个主题互不重复, 没有可供聚合的簇 → 该范式在此负载上无收益可言;
- 与此同时, 该范式在本负载上也**未被证伪**: 它需要"同一主题多条事实"的负载才能被公平检验, 而这样的负载当前不存在;
- 代码骨架 (页 = 可整体重写的文件 / 读写共用地址 / 真相在文件 / 治理策略做成配置而非提示词) 经盲审评定为干净, **保留为候选后端, 不合并进主线**。

**下一步若要重新检验该范式, 前提是先有负载**: 找到或构造"同一实体/N 条事实"的真实数据 (例如长期使用后同一项目的多次决策记录), 再按 §5 的修正方案 (统一 oracle / 统一预算填充策略 / 加负对照臂 `A''=条目形态+同款打分器` / 加不限预算上界臂 / 按词面重叠分层报告) 重做对照。在缺少该负载之前, 任何"Wiki 更好/更差"的结论都不成立。
