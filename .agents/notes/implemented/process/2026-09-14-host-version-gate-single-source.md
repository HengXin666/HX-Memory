# Agent Note: 门禁装载的宿主版本与 package.json 同源

Status: implemented

## Problem

`boot-smoke.yml` 曾硬编码 `npm install -g @deepseek-ai/dsh@0.1.2-rc.1`, 而
`package.json` 的 `peerDependencies` 描述的是插件**受支持**的宿主范围。两者是不同的东西,
却从来没有被强迫对齐过 —— 于是 CI 长期在测一个**不受支持**的组合: 门禁装 0.1.2-rc.1,
用户跑 0.1.5-rc.1。

这不是理论风险, 已经造成过实际后果。2026-09-14 的
[远程端点整组 404](../bug-fix/2026-09-14-typert-remote-404-cross-instance.md)
正是"宿主版本差异"造成的缺陷, 而门禁之所以没有提前发现, 恰恰因为它跑的是另一个版本:
**门禁测的版本与出问题的版本不是同一个, 这是缺陷能活下来的直接原因。**

## Decision

宿主版本只有一个来源: `package.json` 的 `dsh.host`; 门禁装的版本由
`scripts/lib/host-version.mjs` 解出来, YAML 里不再出现版本字面量。

**口径: 装 `latest`, 并且它必须落在 `dsh.host` 内。** 三条理由各自对应一个失败模式:

1. **装 `latest`** —— 用户执行 `npm install -g @deepseek-ai/dsh` 拿到的就是它, 而本次缺陷
   正是 latest 从 0.1.1-rc.2 跳到 0.1.5-rc.1 时发生的。测 latest 才是在测"用户会遇到什么"。
2. **刻意不装"范围内的最高版"** —— 例如 `dsh.host` 为 `^0.1.7-rc.2` 时会解析到 `0.1.7-rc.3`
   (若上游推了那个版本, 它通常挂在 dist-tag `next`), 那是默认安装拿不到的版本。测它等于换了个
   "用户没有的组合", 回到同一个错误里。
3. **latest 越界时大声失败, 不降级** —— 上游把 latest 推到范围外, 意味着**用户已经被推到
   插件不支持的宿主上**。这时 CI 换一个范围内的版本去跑绿, 恰恰是删掉了唯一能看见这件事的信号。
   失败信息给出两个可执行选项: 适配并抬高 `dsh.host`+`peerDependencies` (附真机冒烟),
   或明确保留旧范围并接受 CI 停下。

解析与判定都交给 npm 自己的解析器 (`npm view <pkg>@<spec> version`): 不引入 `semver` 依赖
(本仓库没有, 也不该为一段胶水加一个), 且"会不会装它"的判定与 `npm install` 天然一致。
`tests/s1/host-version.test.ts` 用假 exec 覆盖四种情形: 取 latest 而非最高版、latest 在范围内
被接受、latest 越界抛错、解析不到抛错 (而不是返回空串让门禁变成"没测宿主")。
`boot-smoke.yml` 里解析步骤用 `set -euo pipefail` + `test -n` —— 只写
`echo "version=$(...)"` 的话, 命令替换失败会被 `echo` 的成功掩盖。

## Alternatives considered

**保持现状 (YAML 里写死版本)。** 它已经放过了一次真实缺陷; 而且"版本写在哪"本身没有可见性,
改了 peer 忘了改 YAML 不会有任何提示。

**跟 `dsh.host` 的下界走 (装最老的受支持宿主)。** 抓的是另一类回归 —— "插件用了新宿主才有的
能力" (本仓库历史上真实发生过: 0.1.1 上设置命名空间根本不出现)。但它**看不见**本次这类缺陷。
两类都重要, 因此理想形态是矩阵 (下界 + latest 各跑一次); 本次只落地 latest, 下界通路仍是空白 ——
见下面的"未覆盖"。

**让 CI 读 `peerDependencies` 直接当安装版本。** peer 的语义是"兼容范围", 收成精确版本会让
补丁版升级 (0.1.5-rc.2) 报 unmet peer, 而实测它对 marker 机制无影响。用一个**独立的**
`dsh.host` 字段, 比借用 peer 的语义更诚实: 它只回答"门禁装哪个"。

**干脆不装宿主, 只跑单测。** 本次缺陷证明了单测结构上看不到"宿主与插件的模块身份差异"
(见 bug-fix Note 的证据链)。真机门禁不是可选项。

## Consequences

- 换来的: 任何"宿主版本差异"类回归现在能被 CI 捕获 —— 改 `dsh.host` 或上游发版都会改变
  门禁实际装载的宿主, 无需改 YAML。上游把 latest 推出范围时, CI 停在"用户装到不支持的宿主"
  这一个明确结论上, 而不是继续绿。
- 换来的: 门禁装载的版本现在与用户实际拿到的版本一致 —— 本次缺陷的修复 (协议对齐到当时的
  最新宿主) 因此是被同一个版本验证过的, 不再有"测 A 修 B"的错位。当前 `dsh.host` 是
  `^0.1.7-rc.2 || ^0.2.0-rc.1` (2026-09-29 为适配 0.1.7 的设置契约抬高, 见
  [dsh 0.1.7 宿主适配](../bug-fix/2026-09-29-dsh-017-settings-contract.md))。
- 付出的: CI 多一个联网解析步骤 (`npm view`)。它本来就联网装宿主, 不增加实质成本;
  但网络失败会让这一步失败 —— 这是刻意的: 解析不到版本时停下来, 比装一个猜测的版本好。
- 付出的: 上游发 `latest` 会改变 CI 行为, 因此上游发版可能让门禁变红。这是选 latest 的
  固有代价, 换来的是"在 CI 里先红, 而不是在用户面板上先红"。

## Testing

- `tests/s1/host-version.test.ts` (10 条): 用假 exec 覆盖上述四种情形; 另有一条文本守卫断言
  `boot-smoke.yml` 不再出现硬编码版本、且确实调用了解析脚本。
- `scripts/verify.sh` 的 `lint` 段覆盖 `scripts/**`, 解析脚本随之进入静态检查。

## 未覆盖: 下界宿主没有被自动测试

本次只落地了 latest 通路。`dsh.host` 下界 (`^0.1.7-rc.2 || ^0.2.0-rc.1` 里的 0.1.7-rc.2)
与 latest 现在已不是同一个版本, 所以这个空白**是可见的**: 旧宿主的两条回退路径
(`installSection` / `register`) 只有单测覆盖 (宿主桩), 没有真机门禁。一旦上游发布更高版本,
"最老受支持宿主"就完全无人测。
届时要么加矩阵, 要么明确声明"只支持 latest 及其所在小版本"。这是有意的遗留, 不是遗漏。
