# 记忆系统横向评测报告

目的: 记录"同一批数据、同一套 case、同一 LLM 与嵌入模型"下, 本仓库与几个开源记忆系统的实测对比。
边界: 只覆盖**检索质量**与**抽取噪声**两个面; 不评部署成本与许可证合规 (见 `open-source-landscape.md`)。
与代码的关系: 骨架在 `bench/`; 被测系统之一是本仓库 (经 `src/app/stack.ts` 组装)。

> [!NOTE] 未实现: 端到端问答轴 (原始对话 → 问答准确率) 尚未开跑, 需要 LLM judge 与更大 case 集。

> 收敛后的结论、适用范围与行动项见 [benchmark-review.md](benchmark-review.md);
> 本文保留完整过程与逐项论证。

## 一、被测系统

| 系统 | 版本 | 许可证 | 接入方式 |
| --- | --- | --- | --- |
| HX-Memory (本仓库) | 0.1.0 | Apache-2.0 | `bench/runners/hxmem.ts`, 5 个通道变体 |
| mem0 | mem0ai 2.0.20 | Apache-2.0 | `bench/runners/mem0_system.py`, raw 与 infer 两种模式 |
| Basic Memory | 0.22.1 | **AGPL-3.0** | `bench/runners/basic_memory.py`, 逐条 markdown note + FTS |
| Graphiti | graphiti-core 0.30.2 | Apache-2.0 (图库 FalkorDB Lite 嵌入式) | `bench/runners/graphiti_system.py`, **未完成, 见下** |

同义改写 case 由 `bench/lib/paraphrase.py` 用真实 LLM 生成, 并要求与原文的字符 bigram
重合度低于 0.35 (实测平均 0.11) —— 这是唯一能体现"语义 vs 词面"差距的一层。

受控变量: 同一个 LLM (经本地代理指向同一上游模型) 与同一个嵌入模型 (本地 bge-small-zh-v1.5, 512 维)。
所有系统由 `bench/score.py` 用**同一个打分函数**计算, 按源条目去重, 弃权类单独统计。

## 二、语料与 case

语料: 从真实记忆库只读导出 **80 条** (排除 shadow)。case: **171 个**, 五层 ——
唯一子串 67 / 共享词面 53 / **同义改写 40** / 多跳 6 / 弃权 5。

case 是**机器生成且可验证**的: 词面探针用"在全库中唯一"判定, 弃权类的关键词经词边界校验确认不出现,
同义改写的字面重合度由 bigram 阈值卡住。

## 三、结果 (k=10, recall 口径)

含 171 个 case (含 40 条同义改写)。下表是**融合权重标定与 MMR 归一化之后**的结果:

| 系统 | R@1 | R@10 | H@1 | H@10 | MRR | nDCG@10 |
| --- | --- | --- | --- | --- | --- | --- |
| D 真语义 (bge) | 0.631 | **0.965** | 0.759 | **0.970** | 0.831 | 0.859 |
| B 哈希近似语义 | **0.641** | 0.935 | **0.777** | 0.940 | **0.834** | **0.852** |
| A 纯词面 (无向量无图) | 0.684 | 0.947 | 0.831 | 0.952 | 0.875 | 0.884 |
| C 哈希语义 + 图扩展 | 0.611 | 0.935 | 0.747 | 0.940 | 0.818 | 0.840 |
| mem0 raw | 0.583 | 0.919 | 0.723 | 0.940 | 0.792 | 0.811 |
| E 真语义 + 图扩展 | 0.583 | 0.965 | 0.711 | 0.970 | 0.805 | 0.840 |
| basic-memory (text) | 0.349 | 0.663 | 0.494 | 0.669 | 0.548 | 0.567 |

`H@k` = top-k 里有没有 gold (区别于 `R@k` 的"答全了没")。多 gold 的 case 上两者会明显分叉 ——
例如 basic-memory 的共享词面 `R@10` 0.672 但 `H@10` 0.672, 而同层本仓库两者接近, 说明它
"要么全中要么全不中"。只看单一指标会得出片面结论, 因此两个都记。

**分层看才有意义** (recall@10):

| 系统 | 唯一子串 | 共享词面 | 同义改写 | 多跳 |
| --- | --- | --- | --- | --- |
| A 纯词面 | 0.985 | 0.986 | 0.825 | 1.000 |
| B 哈希近似语义 | 0.985 | 0.976 | 0.750 | 1.000 |
| D 真语义 | 0.985 | 0.958 | **0.900** | 1.000 |
| mem0 raw | 0.955 | 0.917 | 0.850 | 1.000 |

## 四、结论

1. **语义通道的价值只在同义改写层显现。** D 真语义 0.900 vs A 纯词面 0.825 vs B 哈希近似语义
   0.750 (均为该层 `R@10`)。注意 B 反而**低于** A —— 哈希袋嵌入在同义改写上不是"更差一点",
   而是主动引入噪声。结论是"哈希近似语义有害、真语义有效", 而非"语义无用"。
2. **词面通道仍是最强单通道, 但融合后真语义变体拿到了最高的 H@10。** 这说明正确的用法不是
   "用语义替换词面", 而是"词面主导 + 语义补召回" —— 已落实为 `bm25: 2` 的默认通道权重
   (标定过程见 Agent Note `2026-09-12-fusion-weights-and-mmr-scale`)。
3. **自适应调权的设想被数据否掉。** 按查询的"字面可命中性"分桶后, 向量通道的 top1 正确率在
   任何桶里都不高于词面 (低覆盖 0.500 vs 0.500, 高覆盖 0.463 vs 0.943); 既然它从未在 rank-1 上
   更好, 就没有"该让它主导"的场合。
3. **本仓库的图扩展在当前数据上逐位无差别, 甚至有害。** 语料只有 13 条边且全是 `generalizes`,
   规则本身字面就可命中; E 还把多跳从 1.000 拉到 0.667。要让图有价值, 必须先让写入路径
   产出边 (当前 `entities` 填充率 0%)。
4. **basic-memory 全面落后** (R@1 0.349), 弱项在共享词面与同义改写。它把每条 note 当整体索引,
   长文本里的细粒度匹配不占优。
5. **所有系统在弃权上都失败**, 没有系统会说"我不知道"。这是共同短板, 不是某一家的问题。

## 四之二、Graphiti: 接了但没跑完 (这本身是结论)

Graphiti 的适配器已完成并**部分**跑通, 但**没有**进入上表 —— 因为它在合理时间内跑不完:

- 单条写入约 **20 秒** (每条要一次 LLM 抽取 + 建实体/边 + 社区处理)。80 条语料仅写入就要 ~27 分钟,
  之后 171 个 case 的检索还要逐个走 **cross-encoder 重排 (又是一次 LLM 调用)**。
- 整个流程跑了约 **50 分钟仍未结束**, 已终止。终止时数据库已 2.3 MB, 说明它确实在抽取, 不是卡死。
- 作为对照, 同一份语料: 本仓库 (确定性抽取) 秒级完成, mem0 raw 2 秒, basic-memory 一次性 reindex。

已确认可用的接入要点 (写进适配器注释, 供后续复用):

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| 上游挡 UA | 403 Cloudflare 1010 | 走本地注入 UA 的代理 |
| 需要真 key | 401 INVALID_API_KEY | 代理会透传 Authorization, 必须给真实 key |
| 构造时自动建 reranker | 缺 key 直接抛 `OpenAIError` | 显式传 `OpenAIRerankerClient` |
| 结构化输出 | 400 "response_format type is unavailable" | `OpenAIGenericClient(structured_output_mode="json_object")` |
| `reference_time` 类型 | `'str' object has no attribute 'isoformat'` | 传 `datetime`, 不是 ISO 字符串 |
| 检索返回**边**不是原文 | 事实是改写过的文本, 无法直接对回源条目 | 用 `edge.episodes` 里的 episode uuid 反查源 id |

**抽取质量的非正式观察** (样本小, 仅作方向): 英文实体丰富的事实 (Alice works at Acme Corp...)
抽出 2 节点 1 边; 中文**实体型**事实 (张伟在北京的 Acme 公司担任软件工程师) 抽出 3 节点 3 边;
而中文**抽象陈述型** (如"派生索引必须可全量重建") 抽出 1 节点 0 边 —— 抽象经验类记忆
在知识图谱形态下会退化成孤立节点。这正好是本仓库 `entities` 填充率 0% 的镜像问题。

## 四之三、全上下文基线: 当前规模下, "不做检索"也答得对

方法论要求永远放一个笨基线 —— 如果"把全部语料塞进上下文"就够了, 那么检索质量根本不重要,
这个 benchmark 就在测一个不存在的问题。实测:

| 上下文预算 | 能塞下的条数 | 占语料 |
| --- | --- | --- |
| 8K | 23 | 29% |
| **32K** | **80** | **100%** |
| 128K / 200K | 80 | 100% |

**整个语料只有 16,537 tokens (80 条)**, 32K 上下文就能全部装下。换算成规模拐点:
按当前平均 207 tokens/条, 32K 预算约 **154 条**、200K 预算约 **967 条** 之后检索才成为必需。

各系统每次查询的实际注入量:

| 系统 | 平均返回条数 | 平均 tokens | 占全上下文 |
| --- | --- | --- | --- |
| A 纯词面 | 7.0 | 1,775 | 10.7% |
| B 哈希近似语义 | 7.3 | 1,845 | 11.2% |
| D 真语义 | 10.0 | 2,470 | 14.9% |
| mem0 raw | 10.0 | 2,318 | 14.0% |
| basic-memory | 9.9 | 2,173 | 13.1% |

**这说明什么**: 在**当前这个规模**上, 检索的价值主要来自**省 token 与降延迟**
(省 85%~89%), 而不是"能不能答对" —— 因为不做检索也能答对。
本报告前面所有质量差异, 都应该在这个前提下读: 它们是"同等预算下谁排得更准"的比较,
而不是"没有它就答不出来"的证明。

要让 benchmark 真正测到"检索的必要性", 语料必须扩到 **≥1000 条** (见 §五 的样本量边界,
两者恰好是同一个数量级的要求)。

## 四之四、规模压力 (1000 条): 排序稳定性

真实记忆只有 80 条, 因此按 §四之三 的结论, 必须扩规模才能测"检索的必要性"。
做法: **真实条目原样保留** (所有查询仍指向它们), 另外由 `bench/lib/scale-corpus.ts`
合成 920 条同域干扰项 (模板生成, 字段完整, 在 `stats` 里显式标注)。

| 系统 | 1000 条 R@1 | 1000 条 R@10 | 80 条 R@10 | R@10 变化 |
| --- | --- | --- | --- | --- |
| A 纯词面 (本仓库) | **0.684** | **0.944** | 0.947 | **-0.3%** |
| B 哈希近似语义 | 0.617 | 0.944 | 0.935 | +0.9% |
| D 真语义 | 0.613 | 0.938 | 0.965 | -2.7% |
| E 真语义 + 图扩展 | 0.577 | 0.938 | 0.965 | -2.7% |
| mem0 raw | 0.537 | 0.839 | 0.919 | **-8.0%** |
| basic-memory | 0.339 | 0.648 | 0.663 | -1.5% |

**规模是区分系统的一条关键轴**: 从 80 条扩到 1000 条 (12.5 倍), 本仓库基本不退化
(A 仅 -0.3%), 而 mem0 raw 掉了 8 个百分点。同义改写层最能看出差别: mem0 的 `H@10`
从 0.850 掉到 0.775, basic-memory 稳在 0.250 (它在这层本来就弱)。

token 成本随规模的变化同样重要: 1000 条时全上下文需 92,392 tokens, 而各系统每次查询
只注入 1,677~2,315 tokens (占 1.8%~2.5%) —— **检索从"省 token"变成了"唯一可行"**。

## 四之五、用错指标会得出相反结论 (图扩展为例)

同一批数据、同一个功能, 两个指标给出完全相反的读数 —— 这是本报告最该被记住的一条。

| 读数 | 指标 | 图关闭 | 图开启 |
| --- | --- | --- | --- |
| 一 (全体 171 case) | R@1 | **0.690** | 0.313 |
| 二 (字面不可达的 4 个 case) | 命中率 | 0.250 | **0.750** |

读数一的 gold **全部字面可命中** (这正是 case 生成方式决定的: 探针取自条目自身),
因此图召回的"主题邻居"无从加分, 却以同等权重参与排名 —— 只看到代价。
读数二的目标字面不可达, 图通道是唯一路径 —— 只看到价值。

图候选的 gold 精确率实测 **8.5%** (50/588): 实体共现建的是**主题邻居**, 不是**答案**。

**修法不是开关而是分层**: 图候选作为独立配额的"第二梯队"追加在主榜单之后, 只补位不抢占。

| 模式 | 全体 R@1 | 全体 R@10 | 图专属命中 |
| --- | --- | --- | --- |
| 图关闭 | 0.684 | 0.947 | 0.250 |
| 图参与竞争 (旧) | 0.630 | 0.947 | 0.750 |
| **第二梯队 (新)** | **0.684** | 0.947 | **0.750** |

教训 (与前几轮的 MMR 量纲问题同源): **一个通道"有没有用", 取决于你在什么 case 上、
用什么指标去问它。** 只报单一层级的平均分, 足以让一个有用的功能被误判为有害。

## 五、必须声明的边界

- **样本量不足**: >1000 题才有统计效力 (Miller 2024, arXiv:2411.00640); 131 题只能算内部消融。
- **池化偏差**: gold 由本仓库内容派生, 对词面检索有利; 换系统时须重新独立生成 gold。
- **只有一条轴**: 端到端问答未测; 那条轴上"人工沉淀 vs LLM 抽取"是不可控混杂, 必须单独报。
- **case 类型失衡**: 唯一子串占 39%, 而它是最容易的一层 (所有系统都在 0.95 以上),
  会把各系统之间的真实差距稀释掉 —— 分层数字比总分更可信。
- **同义改写的 gold 单一**: 每条只有一个目标条目, 无法区分"召回了相关但非唯一答案"。
- **Graphiti 缺席**: 它没跑完, 因此上表**不能**被读成"Graphiti 效果差" —— 它只是成本高到
  不适合这个规模的批量评测。结论只覆盖表内三个系统。
- **合成干扰项不是真实记忆**: §四之四 的 1000 条里只有 80 条是真实的, 因此那些数字只能说
  "在该规模下的排序稳定性", 不能说"真实记忆库上的表现"。真实数据在 1000 条量级上的分布
  (长度、同义密度、题材重叠) 可能与合成项不同。
- **80 条规模下检索并非必需**: 全上下文基线表明 32K 上下文就能装下全部 80 条 (§四之三),
  因此**小规模**下的质量差异衡量的是"排序优劣"而非"系统是否必需"; 到 1000 条才反过来。
- **token 成本未进入主表**: 已单独统计 (§四之三), 但尚未与质量合成单一指标 ——
  不同预算下的性价比排序可能与本表不同。
- **写入成本未列为指标**: 本轮只在 Graphiti 上暴露出来; 后续应把"建立索引的墙钟时间"
  作为一等指标记录 (它决定了系统能否用于日常沉淀)。

## 五之二、指标快照: 让报告不会静默过期

`docs/` 里的表格是**手抄**的 —— 检索逻辑一改, 报告不会自动更新, 数字会静默过期。
"过期但看起来权威"比没有报告更糟, 因此加了 `bench/snapshot.ts`:

- 它只跑**不依赖 LLM / 嵌入服务**的确定性臂 (A 纯词面、B 哈希近似语义) 加三项结构指标
  (语料条目数 / 关系边总数 / 有 entities 的条目数), 写成 `bench/snapshot.json`。
- `npm run verify-bench-snapshot` 与快照比对, 漂移超 **0.005** 就失败, 并提示
  "有意变更请跑 `bench/snapshot.ts --write` 并同步更新本报告表格"。
- 已挂进 `scripts/verify.sh` (docs gate 之后)。

**适用范围 (诚实声明)**: 语料来自真实记忆库、含私人内容, **永不入库** (在 gitignore 的 `.tmp/` 下)。
因此在新克隆 / CI 环境缺语料时, 这一步会**明确跳过并打印原因**, 而不是假装通过 ——
它是**本地防漂移** gate, 不是 CI 门禁。要让它进 CI, 先得有一份可公开的语料。

已验证: 篡改快照后 exit code = 1 且打印漂移项; 恢复后 = 0; 缺语料时 skip 且 = 0。

## 六、复现

```bash
python3 bench/serve/embed_server.py &     # 本地嵌入 (bge-small-zh)
python3 bench/serve/llm_proxy.py &        # LLM 代理 (注入 UA)
node --experimental-strip-types bench/lib/corpus.ts
node --experimental-strip-types bench/lib/cases.ts
node --experimental-strip-types bench/runners/hxmem.ts --out .tmp/bench/hxmem-runs.json
python3 bench/runners/mem0_system.py --out .tmp/bench/mem0-raw-runs.json
python3 bench/runners/basic_memory.py --mode text --out .tmp/bench/bm-text-runs.json
python3 bench/score.py --runs .tmp/bench/hxmem-runs.json --runs .tmp/bench/mem0-raw-runs.json --runs .tmp/bench/bm-text-runs.json
```
