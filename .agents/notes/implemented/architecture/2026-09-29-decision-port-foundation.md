# Agent Note: 决策端口地基 — 端口 / 两层回退 / 账本 / 召回闸

Status: implemented

## Problem

2026-09-29 用户实测暴露一个**相关性**缺陷 (不是格式问题): 他问"兼容 dsh 新版本", 而注入进上下文的
9 条记忆是"派生索引重建 / 分词函数 / 语义端口"等跨项目工程规则 —— **一条都不相关**。

根因在触发层: 四条通道里只有一条看输入内容, 而它认的是**正则句式**。

| 通道 | 判据 | 看输入意图 |
| --- | --- | --- |
| always-on 保底 | kind + importance 排序 | **不看** (无条件注入) |
| intent 门控 | 正则句式 (问过去/为什么/上次) | 看, 但覆盖率低 |
| drift 去重 | 话题相似度 | 看 |
| 预算/条数闸 | token 与条数 | 不看 |

实测该会话全部判定都是 `intent=None` —— 用户那句"兼容一下新版本 dsh"与"这个会和输入意图有关吗"
都不在意图库的句式里, 于是意图通道完全没参与, 收到的全是保底通道按分数选的条目。

"这句话是否与候选记忆相关"是**语义判断**, 正则覆盖不了它。而这正是决策端口擅长的形态:
窄判定、高频、单次 ~0.45s、输出原子结果。

## Decision

**建立决策端口地基: 端口契约 (kernel) + 适配器/回退/账本/召回闸 (adapters)。默认不启用。**

### 1. 端口契约放 kernel, 实现放 adapters

`src/kernel/ports-decision.ts` 只声明形状 (`DecisionPort` / `DecisionQuestion` / `DecisionOutcome` /
`DecisionCapabilities`), 与 `ports.ts` 里其余端口同一纪律: **kernel 只依赖端口**。
实现 (子进程桥到 JEV) 在 `src/adapters/decision/jev-adapter.ts`。

**能力声明**是契约的核心 (不是装饰): 适配器自报 `deterministic` / `needsVoting` / `parallelQuestions`,
于是调用方能写"与实现无关"的代码 —— `if (!caps.needsVoting) samples = max(samples, 7)`,
而不是写死"JEV 要投 7 次票"。

三条硬纪律写进契约头注, 因为它们约束的是**调用方**:
state 的措辞权重高于问题本身 (写结论会让判定反转); 一致性 ≠ 正确性 (状态模糊时它会稳定地给
同一个错答案, 实测 12/12); 端口是路由器不是权威。因此本层不提供任何 `isCorrect` 式的名字。

### 2. 两层回退: 单次没把握 → 升级; 系统性失灵 → 熔断

`fallback.ts`。第一层判据是**信号**而非"正确答案": `agreement < agreeMin` (采样在分歧) /
`sharpness < sharpMin` (候选没区分开) / 报错。第二层判据是**统计的**: 连续 n 次升级,
或窗口升级率超阈值 —— 单次升级解决不了"它整体已经不对了" (提示词换坏/模型降级/上游改行为)。

熔断期内**连判官都不调**, 省掉那 0.45s —— 这就是用户要的"失败 n 次就不显示"。

熔断状态**落盘** (`<root>/decision/<name>.json`): 不落盘的话每次热重载/重启都从头犯错,
而热重载在本仓是常事。

### 3. 可用性探测: 配置缺失与调用层故障必须分开

`probe()` 探一次真调用。`no_key` / 目录不存在 ⇒ **配置缺失**, 在修好前永远不会成功 ⇒
直接跳过调用 (实测耗时 0ms, 不白花 0.45s); 超时 / 上游 500 ⇒ **调用层故障**, 可能自愈 ⇒
交给回退控制器按 n 次统计。

两者都在 `ok=false` 里, 但处置完全不同 —— 这条区分是用户点名的"评判可用性"的实质。

### 4. 账本: 熔断与降级必须可查

`decision-log.ts` 复用 `JsonlLedger` (按天分文件 / 行数上限 / 保留期 / best-effort 在
本仓已有唯一实现)。四态而不是布尔: `used` / `upgraded` / `circuit` / `error` ——
后两者分开, 因为处置不同 (等冷却 vs 去修环境)。

`degradedRate` = (upgraded + circuit + error) / total, 回答用户的问题"判官最近到底有没有在工作"。

### 5. 召回闸: 判官只能收紧, 不能放宽

`recall-gate.ts` 只判**"是否抑制本轮召回"** (用户选定: 只做二值决策, 不判"召回哪几条")。
理由是判官的能力边界: 让它从 20 条里挑 3 条等于要它做生成/排序, 而它是概率模型。

返回 `suppress: boolean`, **默认 false**: 判官说"不相关"时跟着收紧; 判官说"相关"时
**不额外放宽** (仍是既有行为)。于是判官失灵的最坏后果是"按老行为走", 而不是"多注入噪声"。

判据是**出口方向**而非"id 有没有用"的同一思路。

### 6. 默认不启用, 但接线真实可达

`enabled` 默认 false (设置项 `decisionGate`, 或 `HX_MEMORY_DECISION_GATE=1` 临时打开)。
用户明确"先做地基" —— 把判官接进每轮注入会引入一次 ~0.5s 同步开销, 那是需要拍板的取舍。

**但不悬空**: `verify-structure` 的悬空模块检查把它抓了出来 (5 个模块零产品引用) ——
本仓吃过"机制在、没接线"的亏 (`src/wiki/` 曾 1014 行零引用, 靠人工 grep 才发现)。
因此接线到组装根 (`decision-wiring.ts`), 代码路径真实可达、状态可解释。

## Alternatives considered

**在 TS 里重写一遍判官调用 (HTTP + 账号池 + 投票)。** 两份实现必然漂移 —— 本仓反复踩过
(见 `formatRetrieval` 与 `formatEntryLine` 两套行格式的教训)。走子进程桥接既有实现,
单一实现且已被真机验证。

**让判官判"召回哪几条"。** 输在延迟与能力边界: 候选全列进 state 会让输入随候选数增长
(而判官在每轮同步路径上), 且挑取是生成/排序任务, 不是原子判定。**否掉**: 只判是否, 选条仍由
既有的确定性排序 (分数 + 预算 + 条数闸) 负责。

**判官失灵时不注入任何记忆 (完全静默)。** 直接违背 `r00155cdb954e41c7` (保底通道不得依赖模型自觉),
且实测主动检索率仅 6.7% —— 模型不会自己补上那一次查询。**否掉**: 降级目标是**既有的保底 + 意图通道**。

**只做一层回退 (单次没把握就升级)。** 提示词换坏之后每一步都要先白花 0.45s 再升级;
而只有第二层则会把单次异常当成系统性失灵。**两层都要**。

**把熔断状态只放内存。** 热重载会清零, 于是熔断永远追不上失灵 (本仓的热重载是每次改代码都发生的事)。
**否掉**: 落盘, 且用原子替换写 (进程在两次写之间被杀不会留下半个 JSON)。

**报错不计数熔断 (只有"没把握"才熔断)。** 我最初按这个写, 但实测与设计意图不符:
上游 500 会让每轮白花 0.45s 的无效开销, 而"报了错还每轮继续试"正是要停止的行为。
用户 2026-09-29 选定: **两种都算**。账本仍把 `error` / `circuit` / `upgraded` 分开记, 熔断口径
统一但追因要能区分。

**把开关做成"读一次配置"而不是函数。** 与 `autoEvolve` / `episodeRetentionDays` 同一教训:
读一次快照意味着面板改动不生效, 且**无报错**。**改成函数式** (`readSettings: () => ...`),
且 `wireDecision` 自己从全量设置里窄化出它要的两个键 (组装根不必知道决策层关心哪些设置)。

## Consequences

**换来的**: 一条与实现无关的决策能力通路 —— 换模型只改 `wireDecision` 里构造哪一个 `DecisionPort`,
业务代码一行不动。三层降级保证它**不会**让记忆失效。

**付出的**: 新增 5 个模块 (`ports-decision` / `fallback` / `decision-log` / `jev-adapter` / `recall-gate`)
+ 1 个接线模块。组装根因此被顶到 403 行超限, 按职责把决策接线整段移到 `decision-wiring.ts`
(顺带把"关心哪些设置"的知识也移出组装根), 回到 397 行。

**明确放弃的**: 本次**未**把判官接进注入路径 —— 注入行为与接入前逐字一致 (默认关)。
接线只到"可达且可解释"的程度。

**负向保证** (每条都有测试钉住):
- 没有实现 → 与"没有这层"完全一致 (不抛错、不抑制);
- 判官报错/没把握/熔断 → `suppress: false` (降级绝不能变成抑制, 否则记忆静默消失);
- 空输入或无候选 → 不调判官 (不浪费);
- `doctor` 抛错不致命; 实现没有 `doctor` 能力不阻塞;
- 不传 `log` 时判定照常工作 (落账是可选的可观测面, 不是功能依赖)。

## Testing

`tests/s2/decision-port.test.ts` (23 条) 覆盖两层回退、熔断与半开、状态落盘与损坏容错、
探测的两条分支、召回闸的三条降级路径、账本四态与 `degradedRate`。**全部用桩实现** ——
单测依赖网络会变成"时红时绿", 那比不测更坏; 真机由冒烟与探针覆盖。

这套测试在写的过程中抓出**三个真实缺陷** (都是实现错、测试对):
1. `maybeTrip()` 只在升级时检查窗口率 ⇒ "散发式失灵" (升级/成功交替) 永远抓不到,
   而窗口率存在的唯一理由就是抓它;
2. `DecisionRecord.at` 声明了却从没写进记录 (只用作文件名) ⇒ 读侧按 `at` 过滤时会错;
3. `degradedRate` 漏算 `error` ⇒ "判官一直报错"在指标上不可见, 而它恰是最常见的失灵形态。

真机验证 (人工探针, 非单测):
- `doctor` 可用: `ok=true`, **延迟 476ms**, 正确答出 1+1=2;
- 真实判定: 用户原话"兼容一下新版本 dsh, 记忆插件好像失效了" → **`suppress: true`** (546ms),
  而"派生索引为什么要能全量重建" → `suppress: false` —— 正是本 Note 开头那个缺陷的修复证明;
- 配置缺失: `missing-config`, 判定**耗时 0ms** (未起子进程), 走既有通道。

`verify.sh` 全绿 (除 bench 漂移 —— 那是会话前既存的检索层改动, 与本层无关);
`verify-structure` 137 文件 + 21 脚本通过; 全量 `vitest run`: 173 文件 / 1258 测试。

⚠ 桥接层有一处字段名归一必须记住: Python 侧 `doctor()` 自报 `latency_ms` (snake_case),
而本仓契约用 `latencyMs` —— 不做归一 TS 侧永远读不到延迟, 而"判官多慢"正是可用性判断的依据。
