HX-Memory 触发层设计

对标市面长期记忆系统 · 回答"AI 怎么会想到去查记忆" · 2026-09

一句话结论: 市面方案大多把"何时查记忆"交给模型自觉(工具调用)或无条件全量注入, 两者都有明确缺陷 —— 前者该查时不查, 后者吃预算且引入噪声。 HX-Memory 的做法是代码强制的四通道触发: 与模型是否"想起来"解耦, 同时保留模型主动深挖的能力。

发现 1: 触发方式只有三种, 且大多是最弱的一种

模型自觉 (最多) — mem0 SDK、Graphiti、claude-mem、Basic Memory、LangMem、MCP memory server: 提供工具, 指望模型想起来调。
无条件注入 (Letta / VCP) — 声明式占位符或 system/ 常驻, 每轮必进。
hook 强制 + 门控 (ai-memory / MemOS) — 中间件判定后注入, 最接近我们认为正确的形态。

发现 2: 只有少数项目把"该不该查"当成一等工程问题

绝大多数项目的文档只讲"怎么存/怎么搜", 对"模型何时会想到搜"没有机制。 VCP 与 Letta 用声明式注入解决了"必进", 但代价是常驻内容吃预算; ai-memory 的 hook 方案最完整 (模式库 + 置信度门控 + 话题漂移 + 自适应预算), 但只在 Claude Code hook 生态内, 且没有"always-on 保底"这条线。

二、问题拆解: 模型为什么"不知道要查"

  • 模型不知道自己的知识边界。它无法可靠区分"我不知道"与"我知道但记错了" —— 于是默认用参数记忆作答 (幻觉自足), 不触发检索。
  • 工具调用是概率行为。调用与否取决于提示词、上下文压力、任务形态, 同一份记忆在不同轮次表现不一致。
  • 成本与噪声的反向压力。为避免"每轮都查", 常见做法是让模型自己判断 —— 这恰恰把可靠性交回给了不可靠的环节。
  • 无绑定即失效。声明式方案 (含我们 v1 的 Binder) 只对"配置过绑定的项目"生效; 新项目/没配置的项目完全无记忆。

三、HX-Memory 的答案: 四通道触发

与旧做法的差别

场景旧实现 (只有项目绑定)四通道触发
项目没配绑定, 用户下普通指令零注入 记忆完全失效always-on 规则与关键事实必达
用户问"上次这个问题怎么解决的"零注入 (除非绑定了信号词)intent 命中意图 → 召回具体 lesson
换了话题但没提回忆线索沿用旧注入 内容可能已失效drift-refresh 强制重查
同一话题连续追问 5 轮每轮重复注入 吃预算去重 只注一次
模型完全没想起要查无保证代码强制 与模型自觉无关

四、还能更好: 模型主动深挖 (意识引导)

代码通道给的是通用保底; 模型若能意识到"这里有历史", 主动检索能拿到更贴题的具体细节。 因此两条并行, 缺一不可:

① 代码强制 (可靠性)

always-on + 意图门控 + 漂移重查 + 去重。与模型是否"想起来"完全解耦 —— 这是"AI 不知道要查时记忆也生效"的答案。

② 意识引导 (精度)

指引与工具描述明确写出什么样的提问形状该去查 (问理由/问上次/问约定/问既有做法), 并说明"查不到就是真的没有, 不要编造"。工具描述按 MCP 最佳实践写明使用时机而非只说能力。

五、结论与取舍

  • 不把可靠性押在模型自觉上。工具调用保留, 但只是"精度增强", 不是"唯一通道"。
  • 不做无条件全量注入。always-on 只放"不变量"(已确认规则 + 关键事实), 受 400 token 预算约束; 具体历史由意图/漂移通道按需召回 —— 避免"lost in the middle"与预算膨胀。
  • 每次决策都留痕。mode + reason + budget 可审计, "为什么这轮没注入"能被回答。
  • 已知边界 (诚实记录): 意图库是模式匹配, 覆盖不到的表达会漏 (可扩 DEFAULT_INTENTS); 中文指代型追问靠显式规则兜底; always-on 首次预热有 50ms 硬时限, 超时则该轮退化为无保底 (下一轮补齐)。
