# Agent Note: 实体反查的瓶颈在检索配额而非建边策略

Status: implemented

## Problem

评审文档的行动项 1 是"让边提供新信息" —— 依据是上一轮实测"133 条 relates 边里 48% 两端字面已可互找"。
本轮去验证这个判断, 结论是**它错了**: 真正的瓶颈不在写入期建边, 在检索期的图配额。

## Decision

本轮不改进建边策略, 而是把**测量能力**补上, 并把结论写回评审:

- 新增 `bench/lib/entity-cases.ts`: 生成 **entity_only** case ——
  query 取自 A 的唯一探针, 目标是 B, 且 B 与 A 的字面重合 <= 0.12, A/B 至少共享一个实体。
  在真实库上生成 **104 条** (旧版 `lib/graph-cases.ts` 依赖已存 relations, 只生成了 4 条, 样本量不足以分辨策略差异)。
- 评审文档新增 §二之二, 记录三种建边策略与上界测试的结果, 并把行动项 1 改成
  "改**检索期**实体反查 (建 entities 倒排表 + Query.entity 过滤)"。

## Alternatives considered

**继续调建边打分 (IDF 加权 / 丢弃高频实体)。** 实测全部无效: 三种策略在 104 条 case 上
都是 19/104。原因可量化: 目标只共享 1 个实体, 而其它条目共享 2-3 个,
任何"共享越多越靠前"的打分都会把目标挤到第 11~17 名。IDF 只能把它挪到第 11。

**按实体轮流取 (每个共享实体至少贡献一条边)。** 更差: cap=3/5/10 分别只有 15/17/17。
它换掉了"共享多的优先", 但也丢掉了"哪条更相关"的信号。

**提高 maxStructuralLinks (3 → 6/10/20)。** 边数从 133 涨到 451, 命中从 19 只到 22 ——
没有改善。**上界测试**说明原因: 把共享实体的**全部**配对都建边 (442 条), 也只到 22/104。

**直接把 graphTierQuota 调大。** 实测 6/10/20 都停在 24/104: 追加位再多, 也只是在没有排序依据的
候选池里多拿几条。且它不伤 R@1/R@10 (尾巴不进主排序), 所以不是"有害", 而是**收益有界**。

## Consequences

- 已量化的真瓶颈: 种子实体反查出的候选池平均 **12.9** 条 (中位 14), 目标在该池里平均排 **8.1** 名,
  而 `graphTierQuota` 默认只给 **3** 个追加位。104/104 的目标都在池里, 但位次够不到。
- 派生结论: **写入期建边注定做不好这件事** —— 它必须在不知道查询时预先决定"哪几条相关",
  只能在 12.9 个候选里猜; 查询期的实体反查知道"这一问命中了哪些实体", 可以直接选。
- 因此下一步是架构改动而非调参: 给 `entities` 建倒排表 (像 `tags` 那样),
  给 `Query` 加 `entity` 过滤, 让实体反查**进入主排序**。
  当前 `entities` 只是一个 JSON TEXT 列, 查询期无法反查 —— 这是可查证的现状。
- 评审文档的行动项 1 已改写, 并显式标注"原判断已被实测修正", 避免旧结论继续被引用。

## Testing

- `bench/lib/entity-cases.ts` 在真实库上生成 104 条 entity_only case (旧版 4 条)。
- 五组对比实测 (现状/IDF/丢高频/轮流取/全量上界) 全部可复现, 数字见评审 §二之二。
- 全量 `vitest run` 686 用例全绿; `verify-structure` (80 文件) / `verify-docs` (12 份) /
  `bench/snapshot.ts` (9 项) 通过。
