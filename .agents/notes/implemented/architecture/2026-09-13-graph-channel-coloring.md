# Agent Note: 用真实检索给关系图节点标通道

Status: implemented

## Problem

关系图画出了"哪些记忆有关系边", 但看的人无法回答图上**最值得问的那个问题**:
**这些条目在真实查询下是靠什么被找到的?**

边存在不等于检索时走得通。一条 `mentions` 边可能对召回毫无贡献, 真正把条目捞上来的
是字面通道; 反过来, 图上某个孤立点可能恰恰是某类问题下最稳的命中。这两种落差在原来的图上
完全不可见 —— 所有节点都是同一套中性配色, 颜色只按类型/作用域/项目/状态分, 全都是**静态属性**,
没有一个维度说的是"它在检索时发生了什么"。

而这个仓库已经为可观测性投资过: 调度账本记录"为什么注入/没注入", 检索结果里本来就有
`RetrievalHit.channels` (命中路径)。图缺的正是把后者接上去。

## Decision

新增 `scripts/lib/channel-probe.ts`, 给图上每个节点标出它**实际被哪些通道召回**,
前端新增"着色: 检索通道"一档 (`bm25 / vector / graph / tag / entity / recency / rules`),
并在详情面板列出"因为哪几个问题被召回"。图例带每通道计数与"未召回"计数。

关键设计取舍:

- **读数必须来自真实检索器, 不能从字段猜。** "有 `entities` 字段就标 entity 通道"标的是
  **配置**; 而 entity 通道要种子驱动、要共享实体计数达标才出手, 二者经常不一致。
  探针因此真的构造 `HybridRetriever` 并调用 `retrieveSync`。
- **探针把语料复制进临时库 (mkdtemp) 再检索。** 检索需要 FTS5 索引, 直接对真实根目录跑会在
  它下面建/改 `index.sqlite` —— 而预览脚本的承诺是**只读**。多付一次全量写盘, 换"只读"这个
  承诺字面为真 (已用 md5 与 mtime 逐项验证真实库未被触碰)。
- **`purpose: "recall"` 而不是默认的注入语义。** 注入语义下规则保底通道会把每个查询的读数都
  染成 `rules` (规则不受覆盖率过滤, 数学上碾压字面命中), 那样标出来的颜色全是同一色,
  没有任何区分度。
- **问题只从标签/实体派生 (或由 `--queries` 显式给)。** 绝不拿整条内容当查询: 那等于用答案
  问答案, 每条都会命中, 读数失去全部信息量。
- **未召回的条目渲染成灰色, 并且把覆盖率明确写在状态栏。** 大片灰是**结论**
  (这些条目在当前问题分布下召回不到), 不是渲染失败; 不报告读数的话看的人分不清这两者。
  真实库实测: 71 个派生问题, 覆盖 69/85 条。
- **多通道命中时按固定优先序取一个颜色。** 单一颜色必须有确定的选择规则, 否则同一张图两次
  渲染可能长得不一样, 而颜色抖动比"取第一个"难排查得多。

## Alternatives considered

**按静态字段着色 (有 entities 就绿、有 relations 就紫)。**
零成本, 不碰检索器, 也不会写任何东西。否掉它的理由是**它回答不了问题**: 这一维要说明的是
"检索时发生了什么", 而字段只说明"库里存了什么"。用配置冒充行为, 恰好是这个仓库反复拒绝的
那类假证 —— 图看起来有信息, 实际只是把字段换个颜色画了一遍。

**直接对真实根目录跑检索 (不复制临时库)。**
实现最简单, 读数与真实库**完全一致** (没有"临时库重建导致的统计偏差")。否掉它是因为它会
破坏预览的核心承诺: 检索会建/改 `index.sqlite`, 而"单文件预览只读"是这个工具被信任的前提
(它被允许直接读 `~/.dsh/hx-memory`)。代价换来的还有一个好处: 探针不需要真实库可写,
在只读挂载或归档快照上也能用。

**把通道信息写进预览前端、由前端内嵌一份检索实现。**
那样就不需要 Node 侧探测。但浏览器侧要重实现 RRF 融合与全部通道, 等于维护第二套检索语义 ——
两份实现必然漂移, 而漂移出来的颜色比没有颜色更误导。

**把问题集合固定成"从内容里抽一句"。**
省掉 `--queries` 参数。否掉: 抽出来的句子与条目本身高度重合, 会让命中率虚高到接近 100%,
图上就没有灰点了 —— 而"哪些条目在真实问题下召回不到"正是这一维最有价值的输出。

**让探针也跑语义通道 (LexicalEmbedder)。**
会更接近全能力读数。暂不做: 预览是离线单文件工具, 加载词典嵌入器有明显启动成本, 而且
"哪些通道在工作"会混入"嵌入器有没有装上"这个无关变量。当前明确只在字面/图/实体等本地通道上标,
需要更全读数时用 `bench`。

## Consequences

换来的是: 图上第一次出现"检索行为"这一维, 且能直接看出**边存在但检索不可达**的落差
(实测 82 节点中 13 条在当前问题集合下未被召回, 多数是纯中文散文, 正是确定性通道的边界)。

付出的代价:

- 生成一次图要多跑 N 次真实检索 (真实库 71 个问题 → 约 0.3s) 与一次全量写临时库。
  对"生成预览"这个频率完全可接受, 但它是**新增成本**, 不是零成本。
- 临时库按 id 重建, 因此依赖"库里还有别的条目"的通道统计会与真实库略有差异。
  本预览只用它标通道、不报告指标, 因此差异不影响它给出的结论 —— 但这是一条**已知偏差**,
  不是"完全等价"。
- 探针的失败是静默降级的 (返回空表 → 图上不出现这一维)。这是刻意的 (预览首先要能看),
  但意味着"没有颜色"可能代表"探测失败"而不是"真的没命中"; 因此状态栏与 stdout 都会明确
  打出"跳过 (没有可用问题)"或覆盖率读数, 让这两种情况可区分。
- `scripts/graph-preview.ts` 现在被测试 import, 因此必须区分"被当脚本执行"与"被 import" ——
  否则单测会顺带重建整张图 (踩过)。

## Verification

- `tests/s2/channel-probe.test.ts` (9 条): 读数来自真实检索 (`bm25` 等)、未召回条目不在表里、
  命中记录带上"是哪几个问题"、**探针不触碰真实库** (`index.sqlite` 的存在性/大小/mtime 逐项比对)、
  无问题时返回空表、空语料不崩; `deriveQueries` 只从标签/实体派生且不把整段内容变成查询。
- 真实库端到端: 71 个派生问题 → 覆盖 69/85 条, 通道分布 `bm25:65 / entity:17`, 13 条未召回。
- 只读承诺单独验证: 生成前后 `index.sqlite` 的 md5 一致, 真实库 1 分钟内无文件被改动。
- `import` 副作用单独验证: 单测运行期间不再打印生成日志, 直接执行仍正常产出。
