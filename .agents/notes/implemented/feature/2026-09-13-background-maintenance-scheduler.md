# Agent Note: 后台维护调度器 (P3 的 ⬜)

Status: implemented

## Problem

`docs/architecture-v2.md` 的 P3 一行里, "调度器" 一直是个 ⬜, 而这个 ⬜ 的实际后果比它看起来严重:
`consolidate` (衰减/TTL 扫描)、`prune` (episode 与账本清理) 此前**只有 CLI 能触发**。
也就是说, 一个只通过 DSH 面板与对话使用记忆的用户, 永远不会有任何东西被整合 ——
事件类条目从不衰减, episode 日志从不清理, 记忆层单调增长。

更糟的是这个缺口**不可见**: 没有报错、没有日志、面板上什么都不会显示。
用户能观察到的唯一症状是几个月后的检索结果变差, 而那时已无从归因。

已有的能力全都"等你来按": CLI 有 `consolidate`, 面板有"主动整理"按钮。
但"等你来按"对**衰减**这类工作是失效的 —— 衰减的语义是"没人用它就该消失",
而"没人用它"恰恰等于"没人会来按那个按钮"。所以必须有东西在后台跑, 且必须在**空闲**时跑。

## Decision

新增一条后台维护通道, 由 DSH 适配层持有, 三层拆分:

1. **判定层** `src/adapters/dsh/scheduler.ts` — 纯函数 `shouldRunMaintenance` + 计时器 `MaintenanceLoop`。
   两个闸门: 距上次**尝试**不足 `intervalMs` → 不跑 (否则每个 tick 都跑);
   距上次会话活动不足 `idleMs` → 不跑 (否则与捕获并发改写同一批真相文件)。
   `lastActivityAt === 0` (本进程还没见过任何活动) **视为已空闲** —— 新起的进程正该做一次维护,
   不能被"从没活动过"永远挡住。
2. **执行层** `src/adapters/dsh/spawn-cli.ts` — 起 `node <cli> maintain --root <memRoot>` 子进程。
   CLI 侧新增 `maintain` 命令 (`consolidate` + `episodes.prune()`), 输出一行 JSON 供父进程记录。
3. **装配层** `src/adapters/dsh/maintenance-wiring.ts` — 唯一读 `settings()` 的地方, 把三者接起来,
   结果写进 `maintenance-log.ts` 的环形缓冲, 由 gateway 的 `maintenance` RPC 投影给面板。

默认 **开启**, 周期 6 小时, 空闲门槛 10 分钟; 设置项 `maintenanceIntervalHours` (0 = 关闭) 与
`maintenanceIdleMinutes` 都**实时读** (与 episode 保留期同一套理由: 面板改动不必重启)。

关键设计取舍:

- **子进程而不是进程内调用。** 维护会批量改写真相文件 (Markdown)。宿主随时可能捕获新记忆,
  同进程内并发写同一批文件会丢写。子进程 + 空闲门槛把"并发"变成"不同时", 而不是靠锁。
  代价是每次维护多一次 Node 冷启动 (~100ms 量级, 周期是小时级, 可忽略)。
- **计时器 `unref()`。** 插件也可能被一次性 CLI 场景加载; 一个活着的计时器会让命令挂住不返回。
- **默认开启而不是默认关闭。** 这个缺口本身就是"默认关闭"造成的: 用户不知道有这个能力,
  于是永远不会打开它。维护是记忆层的固有义务 (条目会变陈旧), 不是可选增强。
  想要绝对不出后台进程的用户可以把周期设为 0, 那时**代码路径照常存在**, 只是不触发。
- **失败必须留证据。** 记录里保存子进程输出尾部, 而不只是 `exit:N`。
  这不是洁癖, 是两个真实踩到的坑: 第一版忘了传 `--root`, 于是 CLI 打 usage 并 exit 1,
  而记录里只有 `exit:1` —— 维护"每次都在跑、每次都什么都没做", 从日志完全看不出来。
- **记录是内存环形缓冲, 不落盘。** 调度账本 (schedule-log) 落盘是因为它回答跨重启的
  "昨天那轮为什么没注入"; 维护只回答"它最近有没有在工作", 面板能看见就够, 不值得再加一份
  保留期管理。代价明确: 重启后历史清空。

## Verification

- `tests/s2/maintenance-scheduler.test.ts` (18 条) 钉住: 两个闸门各自的边界与跳过原因;
  周期 0 真关闭; 构造后不立刻跑; 一个周期只跑一次; `execute` 抛错也被记录且循环不停摆;
  失败记录**带子进程输出**; `HX_MEMORY_CLI` stub 断言 `--root` 真的进了 argv;
  非零退出保留输出; 子进程挂死被超时杀掉 (`killed:SIGKILL`)。
- 端到端一条: 过 TTL 的 `event` 经"调度器 → 子进程 → CLI → 真相文件"后状态真的变成 `expired`。
  这是本改动最容易假绿的部分 —— 单元测试全绿也可能因为漏传 `--root` 而全程空跑, 所以必须有一条
  端到端的落盘断言。
- `tests/s2/remote-methods.test.ts` 的集合比对覆盖新增的 `maintenance` RPC (与 gateway 的
  `@Remote` 字面量对照), 保证客户端不会静默 404。
- `tests/s3/maintenance-replay.test.ts` (6 条) 用**真实的 cordis Context** 装插件回放接线:
  断言 `ctx.plugin` 上 `apply()` 后 gateway 的 `maintenance` RPC 真的可用且默认为开、
  周期改设置当轮生效、空闲窗真的挡住执行、没有 CLI 时如实报 `cli-not-found`。
  用真 Context 而不是手搓假 ctx 是一条**硬要求**: gateway 继承 TypertRemoteService,
  构造时调 `ctx.provide(...)`; 假 ctx 要么报与产品无关的错, 要么被补上从而让"Service 没挂上"消失。

  **这条回放当场抓到两个真实缺陷**, 单测全绿也测不出来:
  1. 组装根**忘了把 `maintenance` 注入 gateway 依赖** —— 面板的维护区块在真机上会永远显示"已关闭"、
     记录永远为空。这正是本功能要消灭的那类"不可见", 却由同一个改动自己引入。
  2. `wireMaintenance` 不透传时钟, 任何时间相关断言只能靠 sleep (慢且必然不稳);
     接上了 `now`/`tickMs` 之后判定才是确定性的。
  教训: "接线层"改动的测试必须跑真实接线 —— 假 ctx 与单测都覆盖不到"参数有没有真的传下去"。

## 三次"看起来成功、实际什么都没做"的失效 (同一个根因)

本改动在实现过程中连续踩到三次同族缺陷, 全都是"进程退出 0 / 记录写成功, 但工作没发生"。
三次的**共同根因**是同一件事: **调用约定没有和接收端对齐, 而接收端的错配是静默的**。
留在这里是因为它们决定了现在的接口形状:

1. **漏传 `--root`** —— CLI 打 usage、`exit 1`, 而记录里只有一个 `exit:1`。
   修: `CliRunOptions.root` 是必填字段 (类型上就不可能忘), 且 `CliRunResult.output` 在**成功时也保留**。
2. **把任务名当 argv 传** —— CLI 只认第一个位置参数, `["consolidate","prune"]` 里的 `prune` 被
   静默丢弃且 `exit 0`; episode 清理从未执行。修: CLI 只暴露**一条** `maintain` 命令,
   `MAINTENANCE_COMMAND` 是唯一调用约定, 任务名不再跨进程传递 (只用于展示)。
3. **episode 保留期没传** —— `EpisodeStore` 缺省 `0 = 永久`, 子进程自建 stack 拿不到面板设置,
   于是 `prune` 是静默 no-op, 每次都报 `prunedEpisodes: 0`。修: 保留期作为 CLI 参数显式传入
   (`--episode-retention-days`), 且 0 仍表示用户选择永久保留。

可迁移的教训: 跨进程/跨层调用里, **"成功"必须有可观察的产出** (那行 JSON), 否则退出码 0 是最弱的证据;
"必填参数"应该用类型钉死, 而不是靠注释提醒。

## Alternatives considered

**在进程内直接调 `ConsolidationService` / `EpisodeStore.prune()` (不起子进程)。**
最省事, 没有冷启动, 也没有 CLI 定位问题。否掉它的是**并发写**这个真实风险: 真相文件是 Markdown,
宿主在会话进行中随时会写, 两个写者落在同一批文件上就是丢写。进程内方案要把空闲判定做到同样可信,
还得自己防重入, 复杂度并不比子进程低 —— 而子进程天然给了隔离与超时 (`SIGKILL`)。
补充理由: 子进程**复用 CLI 的同一份实现**, 不需要在适配层再维护一条"和 CLI 一样的整合路径"。

**用 `node:worker_threads` 代替子进程。**
线程能避免冷启动, 但**不解决并发写**: 同一个进程里两个执行体写同一批文件, 丢写机理完全一样。
它只换了调度单位, 没有换隔离边界。

**默认关闭, 让用户自己开。**
这是最保守的选择, 也是最初的直觉 (后台起进程比进程内计时器更"重")。最终否掉:
缺口存在的原因就是没人会主动打开一个自己不知道的开关。用"默认关闭"修"缺省无维护"是自相矛盾的。
面板上把它显示成"已关闭 (周期 0)"而不是隐藏, 让想关的人一秒钟就能关掉。

**像调度账本一样把维护记录落盘。**
一致性更好, 但要多一份保留期管理、多一点每次维护的 IO。拒绝的理由是**职责不同**:
账本回答"为什么", 维护记录回答"还活着吗"。后者的时间尺度是"最近几次", 内存缓冲足够,
且避免了两套清理逻辑互相纠缠。

**固定在启动时跑一次 `consolidate` (复用既有的启动期 prune 位置)。**
零新概念, 没有计时器。但启动时机与"空闲"无关: 插件刚加载时宿主往往正在恢复会话,
而且长期驻留的宿主可能几周不重启 —— 那正是最需要周期性维护的场景。启动期 prune 保留 (它清的是
启动时刻确定过期的账本), 与本调度器**并存而非替代**。

## Consequences

换来的是: 记忆层的陈旧条目与日志**不需要任何人记得**, 会自动被收敛; 面板与宿主日志都能看到
"最近跑过没有、成功没有、下次什么时候", 于是这个曾经不可见的缺口变得可观测。

付出的代价:

- 插件现在**会起子进程**。默认开启意味着用户在没做任何配置的情况下也会有后台 Node 进程被短时启动
  (周期 6 小时, 每次百毫秒级)。这是本改动最需要 review 的一点; 想要零后台行为就把周期设为 0。
- 维护记录**重启即清空**。跨重启的历史不在它的职责内 (需要那类证据时看调度账本或 CLI 输出)。
- `digest` 仍然是**派生视图** (CLI 每次现算、不落盘), 因此"digest 随新条目刷新"这个 ⬜
  没有被这次改动关掉 —— 本调度器给它留了位置 (`tasks` 可配置), 但它不改变 digest 的存储语义。
- 空闲判定依赖 `runtime.idleMs()`, 而宿主若是**从未有过会话事件**的进程, 会被视为"已空闲"。
  这是刻意的 (见 Decision), 但它意味着一次刚启动就空闲的宿主会较早触发第一次维护。
