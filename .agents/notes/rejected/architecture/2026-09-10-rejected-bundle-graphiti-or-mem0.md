# Agent Note: 整包引入 Graphiti 或 mem0 作为记忆引擎

Status: rejected — 引入第二运行时与不可控数据格式, 违背"真相在文件、内核零依赖"的既有取舍

## Problem

调研市面方案时, Graphiti 的时序知识图谱 (episode → 语义事实 → community 三层 + 边级双时态失效) 与 mem0 的写入期近邻裁决, 都比我们当时的实现成熟。一个明显的省力路径是: 直接引入其中一个作为存储与检索引擎, 我们只做宿主接入与跨项目推广。

## Proposal

把 `MemoryStore`/`Retriever` 端口实现为对 Graphiti 服务的调用 (Python 服务 + 图数据库), 记忆真相交由它管理; 我们保留 Facade 与宿主适配。

## Alternatives considered

**抄机制不抄代码 (最终采纳)。** 把双时态四元组、失效而非删除、三阶段检索、写入期裁决各自实现成我们自己的确定性代码, 保留真相在文件与零依赖内核。

**只引入 Graphiti 的图查询, 真相仍在我们这边。** 看起来折中, 实际是最差组合: 既引入第二运行时与图库运维, 又要自己做双写与一致性恢复, 复杂度高于两个方案之和。

## Acceptance criteria

(未实施, 故不适用。)

## Risks

双写不一致、Python 常驻服务的启动/健康检查成为宿主负担、上游版本漂移导致数据格式不可控; 以及最关键的 —— 真相搬进引擎后, "删库不丢真相""换引擎是接线"这两条既有保证同时失效。
