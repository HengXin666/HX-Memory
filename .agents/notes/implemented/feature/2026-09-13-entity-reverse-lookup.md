# Agent Note: 实体反查 (把 actions/02 的行动项 1 落到检索期)

Status: implemented

前置: [实体反查的瓶颈在检索配额而非建边策略](../architecture/2026-09-12-entity-lookup-bottleneck.md)
(它提出"建倒排 + `Query.entity`"并建议"进入主排序"; 本 Note 实现前者, 实测后修正后者)。

## Problem

`docs/benchmark-review.md` 的行动项 1 是"改**检索期**实体反查 (而非写入期建边策略): 建 entities
倒排表 + Query.entity 过滤", 依据是 §二之二 的实测: 把共享实体的**全部**配对都建边 (442 条,
现状的 3.3 倍) 也只把 entity_only 命中从 19/104 提到 22/104 —— 写入期必须在**不知道查询**的情况下
预先决定"哪几条相关", 它注定只能猜。

而当时的代码里这件事**根本还没开始**: `entities` 只作为一个 JSON 列存在 (`memories.entities`),
既没有倒排表, 也没有任何读路径 —— 检索期的"实体反查"实际是**图扩展通道**在兼顾, 而它给实体候选
的配额只有 `graphTierQuota = 3` 个尾巴位。同一份实测给出瓶颈的量化: 候选池平均 12.9 条,
目标在池中平均排第 **8** —— 3 个补位位次够不到第 8 名。

## Decision

### 1. 实体是**派生物**, 兜底抽取放在索引侧 (`kernel/entity.ts`)

真库的 `entities` 填充率长期 0% (82 条里 0 条): 只有 LLM 结构化器会写它, 而结构化器在多数会话里
不可用。因此新增**确定性抽取**兜底 —— 只抽"标识符形状的专名" (带分隔符的路径名 / 驼峰 / 全大写
缩写), 不抽泛指词与整句话 (错的实体比没有更糟, 这条与 `DEFAULT_STRUCTURER_PROMPT` 的规则一致)。

关键取舍: 它**不写回真相文件**, 只进索引 (与 `tags` 的兜底抽取同一处理)。理由与 FTS 回填相同 ——
实体可从 `content` 重算, 换抽取器时只要重建索引, 不必迁移任何人的文件。

### 2. 倒排表 + `Query.entity` (`storage/index-schema.ts` / `index-reader.ts`)

`entities(memory_id, entity)` 与 `tags` 对称, 但键是**规范化后的小写** (`entityKey`: NFKC + lower +
去首尾标点)。索引与查询共用同一个键函数 —— 两侧口径分叉会让反查**静默**失效 (同一类问题在
分词上已经踩过一次, 见 `kernel/cjk.ts`)。`Query.entity` 是结构化筛选 (与 `tag` 同一档),
走倒排而不是扫 JSON 列。

### 3. 旧库回填: 按**版本水位**, 不是按"表是否为空"

兜底抽取器上线前入库的条目 `entities` 是空的, 不回填则反查对它们永远空转 —— 而且**不会报错**。
判定信号必须是"能被记住的东西": 用"entities 表为空"会**永远为真** (纯中文陈述型条目一条实体都
抽不出, 表本来就是空的), 于是每次打开都全量重算。因此记 `entity_version` 水位, 与 FTS 的
`tokenizer_version` 同一机制。

### 4. 检索期通道: 种子驱动的反查, 走**独立配额的尾巴**

新增 `entity` 通道, 但它的形态由两组实测决定, 而不是设计直觉:

- **它必须是种子驱动的。** 我最初的实现预期是"从查询词抽实体直接反查", 于是先量了一下这个前提:
  104 条 entity_only case 里, **只有 4 条把共享实体写在查询里**, 其余 100 条必须先从字面命中
  拿到种子、再用种子的实体反查。这个读数改变了整个实现 —— 若按查询词反查, 通道在 96% 的
  目标 case 上根本不会触发。
- **它不能进主排序。** 进 `ranked` 时实体候选的 RRF 质量足以把词面命中的金牌挤下去:
  主 case H@1 0.807 → 0.503、H@10 0.912 → 0.830, 而它自己的收益很小。这与图通道当初的
  读数方向完全一致 (实体共现建的是"主题邻居", gold 精确率 8.5%), 修法也一致: 给独立配额的
  尾巴, 只用主榜单没填满时的空位。

实测对照 (80 条语料 / 171 主 case + 104 entity_only case, 确定性纯词面臂):

| 配置 | entity_only H@10 | 主 case H@1 | 主 case H@10 |
| --- | --- | --- | --- |
| 关闭该通道 | 0.0673 | 0.807 | 0.9006 |
| `main` (进主排序) | 0.1058 | **0.5029** | **0.8304** |
| `tier2` maxIds 4 | 0.1442 | 0.807 | 0.9123 |
| `tier2` maxIds 8 | 0.2500 | 0.807 | 0.9123 |
| `tier2` maxIds 16 (默认) | **0.2596** | 0.807 | 0.9123 |
| `tier2` maxIds 32 | 0.2596 | 0.807 | 0.9123 |

`tier2` 与"关闭该通道"的主 case 读数**逐位相同** (H@1 0.807 / H@10 0.9123) —— 这正是分层要
保住的性质 (只补位, 不参与打分竞争)。实体侧在 maxIds=16 处封顶 (候选池有界), 配额同样在 8
处饱和 (配额 3 → 0.154, 8 → 0.250, 20 → 0.250)。

**一次自己踩出来的测量错误**: 上面这张表的中间版本是错的 —— 它来自"扫描多组配置"的脚本,
而当时那四组配置**根本没有生效** (只存在于 `HybridRetriever` 的构造参数里, 生产组装路径
`openMemoryStack` 没有透传)。读数全部相同应当被当成"参数没接上"的信号, 而不是"参数无影响"
的结论。修好透传后数字才出现差异, 并直接改变了默认值 (4 → 16)。这也是把常量集中到
`retrieval/tuning.ts` 并单测"标定项真的被透传"的原因。

### 5. 标定常量集中一处 (`retrieval/tuning.ts`)

四个实体参数此前只存在于 `HybridRetriever` 的构造参数里, 而生产路径全部经 `openMemoryStack`
组装 —— **不透传等于这些设置永远不生效**。我踩到了这个坑: 扫描多组配置得到完全相同的读数,
看起来像"参数没有影响"。现在常量集中在 `tuning.ts` (每个都注明依据与代价), 组装时显式透传,
并且有一条测试专门断言"标定项真的被透传"。

同时拆出 `storage/index-maintenance.ts` (回填) 与 `storage/index-status.ts` (只读自述),
因为 `hybrid.ts` 与 `file-store.ts` 都因本次改动越过 400 行上限。

## Alternatives considered

**照原始设想"查询词抽实体 → 直接反查"。** 更简单, 也不需要种子 —— 但实测 104 条 case 里只有
4 条符合这个前提。按它实现等于给一个几乎不触发的通道写一整套代码, 而测试还会因为硬编码的
fixture 而"通过" (我第一版 fixture 就写错了: 目标与查询仍有共享词, 于是 bm25 自己就召回了它,
断言"关掉通道目标消失"直接失败 —— fixture 与实测口径不一致时, 测试会掩盖而不是暴露问题)。

**把实体反查合并进图扩展通道。** 少一个通道、少一份配额 —— 但两者的**种子口径不同**
(图要 traverse 边, 反查要实体键), 且实测收益差一个量级 (图专属 8.5% 精确率 vs 反查命中目标)。
合并后无法分别标定, 只能一起开或一起关。

**让兜底抽取写回真相文件。** 这样实体就成了人的资产的一部分, 看起来更"诚实" —— 但它会把
一个**可重算的派生物**变成需要迁移的格式: 换抽取器时要么写迁移脚本, 要么接受库里两代口径混用。
索引侧兜底让"换抽取器 = 重建索引", 这正是 `entity_version` 水位存在的意义。

**用 df 加权或丢弃高频实体来缩小反查池。** 上一轮已在建边侧试过 (IDF 加权 / 丢 df>15%),
三种策略读数完全相同 (19/104)。反查侧的高频键 (`ADR` 这类裸缩写) 由**共享计数排序**吸收 ——
共享 3 个实体的候选排在只共享 1 个的前面, 不需要额外的加权。

## Consequences

- 换来的: 实体这条能力从"0% 填充、无读路径"变成端到端可用 —— 写入侧有兜底抽取与倒排表,
  读取侧有 `Query.entity` 结构化筛选与独立的检索通道, 升级路径有水位回填。entity_only 这类
  查询第一次有专门的通道负责 (H@10 0.067 → **0.260**), 且**不牺牲**主排序。
- 真库回填已在本改动中**实际发生**: `~/.dsh/hx-memory` 的 `entityStatus()` 从
  `{rows: 0, entries: 0, version: "none"}` 变为 `{rows: 543, entries: 68/82, version: "1"}`。
- 付出的: 一个低精度通道 (它是"主题邻居"不是答案), 因此只给它独立配额; 以及一份需要随
  抽取器演进维护的水位 (`ENTITY_EXTRACTOR_VERSION`, 改抽取逻辑必须 +1, 否则老条目会停在旧口径
  而反查**不会报错**)。
- 仍然**未做**: 真库上的**质量**验证。回填本身已在真库上发生 (68/82 条获得实体),
  但"回填后真库的反查质量"没有测过 —— 上面所有读数都来自 80 条语料的离线 case;
  也没有面板读数 (只有 `entityStatus()` 这个 API)。
- 未改默认行为的部分: 图通道的种子口径与配额完全没动 (实体通道排在图之后, 且不进 `ranked`),
  因此它的读数可与改动前逐位对照。

## Testing

- `tests/s1/entity.test.ts` (15 例): 键规范化、形状抽取 (含 `HXLoLi` 这种"前导大写串 + 驼峰"、
  实测漏掉它会让 19 条 case 的桥断掉)、泛指词/版本号不抽、**与 pattern 书写顺序无关**
  (按出现位置取值, 否则全大写缩写永远轮不到)、上限 16 的来源、显式字段优先与空数组兜底。
- `tests/s2/entity-index.test.ts` (12 例): 显式/兜底进倒排、大小写无关、`Query.entity`、
  shadow 不可见、更新清旧实体、删除清倒排、空键列表不产生 `IN ()` 语法错, 以及**旧库回填**
  (模拟"表被清空 + 水位缺失"的库, 断言重开连接后能反查到、回填幂等、空库不写水位)。
- `tests/s2/entity-channel.test.ts` (8 例): 字面完全不重合的目标靠种子实体被反查出来、
  关掉通道/配额 0 后它消失 (证明是它拿到的)、**默认不参与主排序** (主榜单与关闭时逐位相同)、
  `mode='main'` 是生效开关、共享计数决定顺序、无实体种子时静默不出现、引擎没有该能力时整体缺席。
- 一条 fixture 教训写进了测试注释: "目标与查询有共享词"会让 case 失去意义 (bm25 自己就召回了),
  第一版 fixture 就是这样"失败"的。
- 全量 `vitest run` 699 → **734 用例全绿**; `verify-structure` (86 文件) / `oxlint` (0/0) /
  两端 `tsc` 通过。
