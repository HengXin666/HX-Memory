# Agent Note: 本地知识库接入 (ai-docs 索引) 与真相文件只读前端

Status: proposed

## Problem

用户提出两件事, 都需要先判定可行性再动手:

1. **把 `/home/hx/Loli/code/HXLoLis/HXLoLi/ai-docs` 当本地知识库索引进来** —— "它除了作为记忆,
   还可以作为知识库一样的东西, 添加 1 个新的接口就可以了吧"。**而"加一个接口"是否够, 需要核实。**
   现状: 本仓库**没有任何**"外部文档目录"的读路径; `MemoryStore` 的真相目录写死为
   `daily/digest/rules` (`TRUTH_DIRS`), 外部 .md 进不来。
2. **记忆的存储能否以文档形式给用户直接查看** —— "能否也以文档的形式给用户可以直接查看,
   而不是放到一个数据库里面……给个前端也可以"。
   现状: 真相**已经是** Markdown (ADR-002), 但面板只提供**经 SQLite 的表格视图**,
   没有"按文件浏览真相"的入口。

**而这两件事共用一个前置判定**: 知识库条目若直接入现有库, 会不会**污染保底注入**。
下面第一节就是这条判定的实测结果。

## Proposal

把 `ai-docs` (42 篇 Markdown / 503 KB / 7448 行) 作为**本地知识库**
接入检索, 与"记忆"共用引擎但**分库、分治理、分注入通道**。

**为什么现在做**: `src/wiki/` (1017 行, 已存在但未接线) 的启用条件是——
"该范式要'一主题一页'才有收益, 而那需要**同一主题出现多次**的负载;
实测本项目语料里主题基本只出现一次 (121/125 互不重复) ⇒ 聚合无对象"。

**实测 `ai-docs` 恰好是那个负载**:

| 指标 | 值 |
| --- | --- |
| 文件 | 42 篇 / 503 576 字节 / 7448 行 / **236 个 H2** |
| 主题总数 | 29; **出现 >1 次的 13 个** (覆盖 **26/42** 篇) |
| 最密主题 | `002-AI/004-记忆` **7 篇** / `002-AI/003-Agent-Harness` **6 篇** |
| 与现记忆库规模比 | 字节 **0.56 倍**; 按 H2 切片条目数 ≈ 236 (现 457) |

⇒ **13 个主题有多次出现**, 满足 wiki 的聚合前提; 且它是**结构化文档** (带 `hxid` frontmatter +
`##` 小节), 不需要走"从对话里提炼"那条贵路径。

## 一、实测: 切片与检索可行 (原型已跑通)

按 `##` 切片 + `hxid` 作 id 前缀, 入现有 FTS:

```text
文件: 42 ⇒ 切片条目: 267
条目字数 中位=573 最大=10534 最小=12

检索验证 (5 个真实问题, purpose=recall):
  [DSH 的预设提示词有哪几个] ⇒ 2 条; top= DeepSeek Harness 提示词全解: 四个预设与每一步投递
  [记忆注入怎么避免重复]     ⇒ 2 条; top= 0x02 写入不是保存, 是传播
  [skill 训练 参数]          ⇒ 3 条; top= SkillOpt: 把 skill 文档当参数来训练
  [RTK 怎么用]               ⇒ 2 条; top= 0x01 核心结论
  [Agent 检索栈 凭证治理]    ⇒ 3 条; top= 自建 Agent 检索栈: 本地化边界、凭证治理与可用性证明
```

**⇒ 5/5 命中正确文档** ⇒ 走现有 FTS + 覆盖率门槛**已经够用**, 不需要引入向量库。

## 二、⚠ 一个必须处置的风险: 知识库条目会**冒充**"跨项目关键事实"

实测 (`always-on.ts:84` 的兜底分支):

```ts
// 非规则分支的末尾兜底
return e.kind === "fact" || e.kind === "preference" || e.kind === "decision";
```

⇒ **任何 `kind:"fact"` 都被放行** ⇒ 若知识库条目用 `fact + scope:"global"`, 它会**无条件进保底注入**。
实测: 一条 34 715 字 (≈11 647 tokens) 的文档**被预算闸门挡住** (`over-total-budget`) ⇒ **不撑爆**;
但**比预算小**的文档会**挤占保底通道** (规则组之外的份额)。

**⇒ 所以"加一个接口"不够**, 需要显式分库:

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A (推荐)** | 新增 `kind: "doc"`, 并在 `always-on` 的兜底分支**显式排除** | 改 1 处判据 + 类型枚举 |
| B | 复用 `kind:"fact"` + `scope:"project"` 指向知识库项目 | **不改代码**, 但会被当"项目关键事实"常驻 |
| C | 只做 `purpose:"recall"` 的按需检索, **不参与任何注入** | 最保守; 模型要主动调 `memory_search` |

**⇒ 推荐 A**: 与"知识库不是记忆"这条语义一致, 且保持 `always-on` 的"只放真不变量"。

**与既有 Note 的关系**: 本 Note **不取代** `2026-09-18-wiki-backend-candidate.md` ——
那条讲的是"**用 wiki 范式替代记忆存储**" (负载是对话序列), 而本条讲的是
"**把已有结构化的外部文档接进检索**" (负载已经是 .md)。
两者共用"切片 + 分层下钻"的思想, 但**触点不同** (那条动真相层, 这条只加一个读路径)。
**若将来启用 wiki 后端, 本 Note 的第 1 节 (`kind:"doc"` 分库) 仍是前提。**

## 三、接入方式: 复用现成机制, 不造新轮子

| 层 | 复用 | 说明 |
| --- | --- | --- |
| 切分 | **按 `##` 切** (与 `src/wiki/page.ts` 的"小节"粒度一致) | 不用固定字符窗口 (那会切断语义) |
| 地址 | `hxid` + 小节序号 | 与 wiki 的"三级地址"同构 |
| 索引 | 现有 SQLite FTS5 + `tokenSet` (已支持中文) | 不引入新引擎 |
| 检索 | 现有 6 通道 → RRF → 覆盖率门槛 | 实测够用 |
| 治理 | `src/wiki/config.ts` 的 **`readonly`** 策略 | 它的注释原文: "只读: 不接受对话写入, 只能由知识管线更新" |
| 更新 | 目录 mtime / 文件哈希比对 | 增量重建, 不全量 |

**⇒ 关键**: 知识库条目 **`source: "kb:<相对路径>`** 前缀, 使"记忆 vs 知识库"可区分
(实测: 同一问题可同时命中两者, 靠 source 前缀能分辨)。

## 四、关于"长文本召回"的调研结论

用户问的核心是"长文本召回, 市面有现成方案". 核实后的判断:

| 方案族 | 是否适合 | 理由 |
| --- | --- | --- |
| **整篇塞上下文** (长上下文模型) | **不适合** | 单篇 34 715 字 ≈ 11 647 tokens; 42 篇 ≈ 58 万 tokens —— 任何预算都放不下 |
| **固定窗口切块 + 向量** (经典 RAG) | **不必要** | 实测 FTS + 覆盖率已 5/5 命中; 向量需中文嵌入模型 (本机只有 `bge-small-en`, 中文全 `[UNK]`) |
| **结构感知切分** (`##` 小节) | **✅ 最合适** | 文档**已有** `hxid` + `##` 结构 ⇒ 天然的分块单元, 且"小节"正是 wiki 规格里的证据最小粒度 |
| **分层下钻** (`src/wiki/recall.ts` 五级) | **已有骨架** | `matchPage → getPage → getEvidence → getEvolution → searchDialogue`; 与 KInfra §5 "Agent 自己决定要查多深"一致 |

**⇒ 结论**: 这个场景**不需要市面上的重型 RAG 方案** ——
它是**结构化文档**, 不是无结构长文本; 按 `##` 切 + 现有 FTS + 分层下钻已经覆盖,
而 `src/wiki/` 那 1017 行骨架就是为它准备的。

## 五、关于"能否以文档形式给用户直接查看"

**它现在已经是了** —— 记忆的**真相在 Markdown 文件** (ADR-002), SQLite 只是**可重建索引**:

```text
~/.dsh/hx-memory/
  daily/     YYYY-MM-DD.md     日聚合 (写入的落点)
  digest/    YYYY-MM-DD.md     提炼条目
  rules/     *.md              已确认规则 (一主题一文件)
  episodes/  *.jsonl           原始对话日志 (ADR-018)
  review/    queue.jsonl       待审队列
  index.sqlite                 派生索引 (可全量重建)
```

**⇒ 所以"查看"不需要新建存储**, 只需一个**只读前端**渲染这些 .md。现状:
面板 (DSH Web 的 `memory` 页) 已能搜索/查看/删除条目, 但它是**经 SQLite 查询**呈现的表格;
**没有"按文件浏览真相"的入口** (那才是 ADR-002 的直接体现)。

**建议 (低风险, 与本次知识库无关, 可独立做)**:
面板加一个**只读的"文件视图"**: 列 `daily/digest/rules` 下的 .md, 点开渲染 (Markdown → HTML),
并显示"这条对应的真相文件 + 行号 + 最近一次索引重建时间"。**它不新增存储, 只新增一个读路径**。

而"知识库"那部分**天然就是这个视图的延伸** —— `ai-docs` 也是 .md, 用同一个渲染器即可浏览。
**⇒ 所以两件事可以合成一个前端**: 左栏是"库"的切换 (记忆 / 知识库), 右栏是 .md 渲染。
记忆侧还多一个"这条从哪来" (episode → 条目 → 规则) 的链接。

## Acceptance criteria

1. `kind: "doc"` 的条目**不进** `always-on` (有一条测试断言: 入 1 条 doc + 1 条 rule, `alwaysOn` 只返回 rule)。
2. `ai-docs` 的 42 篇按 `##` 切片后, `memory_search` 对 5 个真实问题**命中正确文档** (≥4/5)。
3. 重复索引**不产生重复条目** (文件哈希比对: 二次运行新增 0 条)。
4. 文档变更后**只重建受影响的文件** (改 1 篇 ⇒ 索引变更条目数 == 该篇的小节数)。
5. `source` 前缀能区分记忆与知识库 (取一条 kb 条目的 `source`, 断言以 `kb:` 开头)。

## Risks

1. **知识库条目挤占检索配额** —— 267 条 doc 混进 457 条记忆里, 可能让记忆条目排到后面。
   *缓解*: `kind` 过滤 (检索时可按 kind 分流); 或独立库 (`--root` 第二个实例)。
2. **文档漂移** —— `ai-docs` 是活的仓库, 改了文件索引就过期。
   *缓解*: 索引身份 (文件哈希) + 启动时增量比对。
3. **单条过长** (最大 10 534 字) —— 命中后整条注入会吃预算。
   *缓解*: 已有预算闸门挡住超预算项; 更细的做法是按小节而非整篇返回。
4. **与 `src/wiki/` 的重复** —— 两者都可能做"切片 + 分层下钻"。
   *缓解*: 本次**不使用** wiki 的页面模型, 只借它的 `readonly` 治理概念; wiki 仍留作候选后端。

## Alternatives considered

**直接启用 `src/wiki/` 作为知识库后端。** 暂不选: 它的提案已被盲审判定"负载先到位",
而本次的负载是**文档**(已结构化) 而非**对话序列**; 用 wiki 的"一主题一页"去聚合已有的 .md
是重复劳动 (文档的组织已经是一主题一目录)。**⇒ 先用最薄的方案 (切片 + FTS), 观察后再决定是否上 wiki。**

**引入向量库 (Chroma/LanceDB 等)。** 暂不选: 实测 FTS 已 5/5; 且中文向量需要合适的嵌入模型,
本机现有的是英文模型 (中文全 `[UNK]`)。**⇒ 先把免嵌入的那条路走到头。**
