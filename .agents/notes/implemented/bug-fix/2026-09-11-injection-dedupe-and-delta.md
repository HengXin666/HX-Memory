# Agent Note: 注入去重与差量注入 (同一会话不重发常驻记忆)

Status: implemented

## Problem

用户实测: 一次会话里**同一批记忆出现两三遍**, 且随轮次在上下文里累积。
真实会话日志 (session-4cc79f1c) 的第 10 与第 12 个事件是两份注入, 六条规则 id **逐条相同**;
另一条 14 轮的会话注入 7 次 —— 单次约 256 token, 累计约 1.8k token 的同一份内容。

三个互相独立的成因:

1. **整块文本判重**: 会话开始注入的块 (无标题/无框架句) 与预步注入的块 (标题 + 框架句) 永不相等,
   于是首次预步必然重复一份;
2. **块文本不稳定**: 预步每步重新拼块, 条目集合变一条整块文本就变 → 已注入过的条目被整份重发;
3. **通道漏判重**: 会话开始被触发两次时会灌两份完全相同的指引。

更根本的是: always-on 是**不变量**, 没有随轮次变化的理由 —— 逐轮重发既烧预算,
又让同一条记忆在上下文里出现 N 次 (模型会误以为它更重要)。

## Decision

注入行带**稳定 id 标记**, 判重与注入都以"条目 id 集合"为准:

- `kernel/injection-format.ts`: 注入行形如 `- [id] 内容 <!--hx-memory:id=id-->`。
  标记做成行尾注释 —— 人读是可忽略的注记, 代码解析是稳定接口。
- `Binder.injectFor(project, text, injectedIds)` 增加第三个参数: 本会话**已注入过的条目 id**,
  由调用方 (pre-step) 从会话日志解析后传入。召回结果减去已注入集合 = 本轮该给的东西。
- 召回结果按 **always-on 组 / 新召回组** 切分 (`splitTriggerGroups`): 前者是常驻不变量,
  只该在会话开始时进一次; 后者按话题变化, 是逐轮补的主体。
- `prestep.scanPriorInjections` 同时返回"已注入文本"与"已注入 id": 前者兜底, 后者是主判据。
- 会话开始 (session-start) 也做同一份判重, 不再灌第二份相同指引。
- 声明式绑定注入 (有 bindings 的项目) 走同一条差量逻辑 —— 它此前是"每轮全量重发"。
- 命中强化回调只对**实际发出**的条目生效: 被差量过滤掉的这轮并没有被"用到"。

## Alternatives considered

- **只做"整块文本"去重**: 治不了成因 2 —— 块文本本身不稳定, 换一条就整份重发。**否掉**。
- **在 Binder 里持有"本会话已注入集合"**: Binder 是无状态纯逻辑层 (S1 可直接断言),
  引入会话状态会把它绑死在宿主生命周期上, 且 compaction 遮蔽后无法自救。**否掉** ——
  基线必须来自"模型可见的会话历史", 那才是判重的正确语义。
- **把 always-on 挪到 system prompt (不追加进历史)**: 更接近主流做法 (Claude Code / Letta),
  但 DSH 插件没有稳定的 system 区写入点, 且那是宿主决定的事。**本次不做**, 见 Consequences。
- **频繁注入换来的"注意力强化"**: 没有任何证据支持; 实测数据只显示预算被吃掉。**否掉**。

## Consequences

换来的: 同一会话内常驻记忆只出现一次; 后续轮次只补真正的新条目 (差量);
去重口径从"文本相等"变成"id 集合包含", 对标题/框架句的措辞变化免疫。

付出的: 注入行多了一段注释标记 (约 30 字符/条);
基线依赖"会话历史里能找到自己的注入" —— compaction 遮蔽后该基线会退化,
此时行为是**重新注入** (保守但正确, 不会永久沉默);
「一次调用里绑定注入 + 触发注入可能给同一条目」这个较小的问题仍然存在。
