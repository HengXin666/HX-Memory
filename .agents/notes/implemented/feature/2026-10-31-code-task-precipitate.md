# Agent Note: 代码任务上的纠正按范围沉淀

Status: implemented

Decision-ID: code-task-precipitate

## Code

- `src/coding/precipitate.ts`
- `tests/coding/precipitate.test.ts`

## Problem

改代码、定架构、写需求时，用户骂人或明确否定，表示这一轮做错了。现有负面信号会把这件事记成一条 lesson 正文，但下一轮仍靠问句和旧句子像不像才能再拿到。对不上原文的设计问法会空。纯粹的骂人如果抽不出「下次怎么做」，也不该进库。

## Decision

`runTurn` 是 coding agent 每一轮要调的纯函数。普通任务只按工作集注入已有决定，不写库。命中骂人或纠正才分析。分析必须交出 scope、concern、claim。缺任一项就丢弃，骂人原话不入库。

写入键是 scope + concern。同一对再写一条，旧的标成 superseded。文件纠正挂在工作集路径上；需求或架构纠正挂在 `req:` 范围上，不塞进一个随便的文件。下一轮只要工作集碰到这个路径，或任务文本碰到这条需求的匹配词，就把当前决定整表注回，不搜问句。`redo` 为真时，这一轮用 `pack` 重做。

这一步不调用模型。要换成模型，只替换 `analyze`。

## Alternatives considered

**什么都不做 / 复用现有。** 最强理由是 `kernel/negativity.ts` 已经能判定骂人并写出「禁止 X。改为 Y」。它解决不了这次的缺口：下一轮仍然靠词面去碰那条正文，改写过的设计问法拿不回当前决定，而且需求纠正没有独立于文件的范围。

**把骂人原话存成记忆正文。** 下一轮读到的是情绪，不是该怎么改代码。

**用两句话的词面重合决定谁取代谁。** 评测里真实提交几乎不会因旧条，只有几乎同构的句子才会。

## Consequences

**换来的**: 纠正挂在文件或需求上，下一轮碰到同一范围就带上；纯骂不入库；同一关注点的旧决定会退役。

**付出的**: 分析是确定性规则，盖不住没有「只要 / 不要 / 必须 / 别」这类约束的骂人。那种情况丢弃，不编一条决定。

**明确放弃的**: 不把这个函数接进现有 `captureTurn`。接进会改已有捕获语义，而这次要的是一个按代码范围读写的入口。

## Testing

- `tests/coding/precipitate.test.ts`: 普通任务不写库；纯骂丢弃；骂人纠正写入文件范围并在下一轮注入；同键覆盖；需求纠正挂在 `req:`；升成硬约束后仍可注入。
