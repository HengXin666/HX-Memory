# Agent Note: 检索返回顺序必须按综合分降序 (修 MMR 顺序被当排名的缺陷)

Status: implemented

## Problem

`HybridRetriever.retrieveSync` 把 `mmrSelect` 的**产出顺序**直接当排名返回。MMR 的产出是
"相关性 × 差异度"折中的**挑选顺序**, 不是相关度顺序 —— 于是分数最高的条目会因为"与已选项相似"
被排到后面。实测: gold 的综合分 0.0229 全场最高, 却排在第 2 名。

这个缺陷在只开词面通道时影响小 (候选少、彼此不相似), 一旦接入向量通道就被放大:

- 修复前: 真语义变体 R@1 = 0.099, R@10 = 0.710
- 修复后: 真语义变体 R@1 = 0.617, R@10 = 0.974

R@10 从 0.710 涨到 0.974 说明 gold 其实一直**在结果集里**, 只是被排到了 10 名开外 ——
问题出在排序, 不是召回。此前把这条误判为"接入真语义有害", 是错的。

## Decision

`budgeted.kept` 在截断前先按 `score` 降序重排。预算的 `reserved` 语义保护的是"是否入选",
不是"排在第几", 因此重排不破坏规则保底通道。

## Alternatives considered

**调低向量通道权重。** 治标: 顺序错乱与权重无关, 降权只会让 gold 与噪声一起下沉。
实测把权重从 1.0 降到 0.3, R@1 只从 0.617 回到 0.668, 仍低于纯词面的 0.726。

**把 `mmrSelect` 改成输出分数序。** 会破坏 MMR 的本意 —— 它的价值就在于"先挑相关的,
再挑不重复的"; 改成输出分数序等于把去冗余关掉。排序与挑选是两个职责, 该在调用处分层。

**干脆关掉 MMR。** 去冗余对注入预算仍有价值 (避免同一件事占满预算); 实测关掉它 R@1 不变
但返回多样性下降, 属于用错误换错误。

## Consequences

- 返回顺序与 `score` 单调一致, 调用方可以信任 `hits[0]` 就是综合分最高项。
- 依赖"MMR 顺序"的下游行为会变: 实际影响是**同一条被选中的集合**换了个顺序, 集合本身不变
  (预算裁剪的入选集合由 `reserved` + 预算决定, 与顺序无关)。
- 真语义通道从"显著有害"变为"与词面接近但 R@1 仍略低" (0.617 vs 0.726)。语义通道是否
  值得默认开启, 取决于 case 集合是否包含**真正的同义改写** —— 当前 case 全是字面探针,
  结构上无法体现语义价值, 这一条留给后续评测处理。
